# FAMAS — Fleet Administration & Management Automation System

Система за цялостно управление на автомобилен парк и транспортни операции (Fleet Management System), разработена като академичен/дипломен проект за управление на МПС, шофьори, транспортни курсове, ремонти и мониторинг на изтичащи документи.

---

## 1. Архитектура и технологичен стек

- **Frontend**:
  - **React 18** (`react@18.3.1`, `react-dom@18.3.1`) със строга TypeScript типизация.
  - **Vite 6** — бърз инструмент за разработка и компилация на статичните активи.
  - **Tailwind CSS** — съвременен utility-first дизайн с висока ергономичност и четимост.
  - **Recharts** — визуализация на оперативния статус на автопарка и разпределението на курсовете.
  - **Lucide React** — унифицирани векторни икони.
  - **Axios & Context API** — реактивно управление на състоянието и автентикацията.

- **Backend**:
  - **Node.js + Express** с чиста TypeScript архитектура (`tsx` за dev, `esbuild` за production bundle).
  - **JWT (JSON Web Tokens)** & **bcryptjs** за защитена автентикация и криптиране на пароли.
  - **Mongoose (ODM)** за структурирани релации и валидация на данни в MongoDB.

- **База данни (Dual Engine Support)**:
  1. **Вградена (Embedded) MongoMemoryServer**:
     - Позволява незабавен старт без нужда от предварително инсталиран MongoDB сървър.
  2. **Реална MongoDB база данни (Local, Docker или MongoDB Atlas)**:
     - Напълно поддържана чрез променливата `MONGODB_URI` в `.env`.

## 2. Модел на данните и релационни връзки

Системата гарантира релационен интегритет между съставните единици:

```
User (admin / dispatcher / driver)
 │ (1:1 за роля driver)
 ▼
Driver ──(1:1 по желание)──► Vehicle
 │                              │
 │ (1:N)                        │ (1:N)
 ▼                              ▼
Trip (origin, destination,     Repair (cost, mileage,
      cargo, distance, fuel)          description)
                                ▲
                                │ (1:N)
Notification (expiry alerts) ───┘
```

1. **User &rarr; Driver**: Потребител с роля `driver` е свързан с конкретен профил на шофьор. Шофьорът вижда само своите възложени курсове.
2. **Driver &rarr; Vehicle**: Шофьорът може да има постоянно зачислено превозно средство, или превозното средство да се асоциира динамично към курс.
3. **Vehicle &rarr; Trip**:
   - При стартиране на курс (`in_progress`) камионът преминава в статус `in_use`, а шофьорът в `assigned`.
   - При завършване на курс (`completed`) камионът и шофьорът преминават в статус `available`, а изминатите километри (`distance`) автоматично се начисляват към километража на камиона (`currentMileage`).
4. **Vehicle &rarr; Repair**:
   - Всеки ремонт записва разход и километраж.
   - Ако километражът на ремонта е по-висок от текущия на камиона, `currentMileage` се обновява автоматично.
5. **Интегритет при изтриване**:
   - **Забранено е изтриването на МПС или шофьор**, ако има активни (`in_progress`) или планирани (`planned`) курсове (връща `400 Bad Request`).
   - При изтриване на МПС автоматично се прекратява връзката със зачисления шофьор и се изтриват свързаните ремонтни картони.

## 3. Матрица на ролевия контрол (RBAC)

Системата разполага с 3 нива на достъп, защитени паралелно на **Backend (Express Middleware)** и на **Frontend (Protected Routes & UI Controls)**:

| Ресурс / Действие | Admin | Dispatcher | Driver |
|---|:---:|:---:|:---:|
| **Дашборд & Статистики** | Пълен | Пълен | Пренасочване към лични курсове |
| **МПС (Преглед)** | Да | Да | Да (списък) |
| **МПС (Създаване / Редакция / Изтриване)** | Да | Не (`403`) | Не (`403`) |
| **Шофьори (Преглед)** | Да | Да | Не (`403`) |
| **Шофьори (Създаване / Изтриване)** | Да | Не (`403`) | Не (`403`) |
| **Шофьори (Назначаване на камион)** | Да | Да | Не (`403`) |
| **Курсове (Преглед)** | Всички | Всички | Само своите |
| **Курсове (Създаване)** | Да | Да | Не (`403`) |
| **Курсове (Редакция на маршрут/товар)** | Да | Да | Не (`403`) |
| **Курсове (Обновяване на статус / км / гориво)** | Да | Да | Да (за своя курс) |
| **Ремонти (Записване & Разходи)** | Да | Да | Не (`403`) |
| **Управление на системни потребители** | Да | Не (`403`) | Не (`403`) |
| **Преглед на изтичащи документи** | Всички | Всички | За зачисленото МПС |

## 4. Бизнес логика за разход на гориво

Системата имплементира европейския стандарт за изчисление на среден разход на гориво:

$$\text{Среден разход (L/100km)} = \frac{\text{Изразходвано гориво (L)}}{\text{Изминато разстояние (km)}} \times 100$$

1. **На ниво курс (Trip)**:
   - Шофьорът или диспечерът въвеждат реално изминатите километри и зареденото гориво при финализиране.
   - В списъка с курсове се визуализира точният разход в $L/100km$.
2. **На ниво превозно средство (Vehicle)**:
   - Всяко МПС има нормативен разход (`Rated Consumption`, напр. $28.5\text{ L/100km}$).
   - В детайлната страница на камиона се изчислява **реалният среден разход от всички изпълнени курсове** и се сравнява с нормативния (в зелен/оранжев цвят).
3. **На ниво автопарк (Dashboard KPIs)**:
   - Дашбордът агрегира общите изминати километри и общото количество изразходвано гориво на цялата компания.

## 5. Мониторинг на срокове и нотификации

Автоматична фонова и интерактивна система следи сроковете на:
- **Периодичен технически преглед (ГТП)**.
- **Застраховки (Гражданска отговорност / Каско)**.

### Критерии за предупреждения:
- **$\le 0$ дни (Expired)**: Критичен статус (`critical`) — МПС не може да изпълнява курсове.
- **$\le 7$ дни**: Критично напомняне (`critical`) за спешно подновяване.
- **$\le 30$ дни**: Предупреждение (`warning`) за предстоящо изтичане.

### Защита от дублиране (Deduplication) и ескалация:
- Ако вече съществува непрочетено известие със същата тежест за същото МПС, ново известие **не се дублира**.
- Когато срокът спадне от предупредителен ($\le 30$ дни) до критичен ($\le 7$ дни), предишните предупреждения автоматично се архивират/маркират като прочетени, а на потребителя се показва актуалното критично известие.

## 6. Демонстрация пред изпитна комисия (Защита на проекта)

### Вариант А: Незабавен старт (Embedded MongoDB)
```bash
# Инсталация на зависимости
npm install

# Зареждане на демо данни
npm run seed

# Стартиране на системата
npm run dev
```

### Вариант Б: Демонстрация с реална MongoDB база данни (Docker Compose)
В проекта е включен готов файл `docker-compose.yml`, съдържащ MongoDB 7.0 и **Mongo Express** (уеб интерфейс за разглеждане на базата):

1. Стартирайте Docker контейнерите:
   ```bash
   docker compose up -d
   ```
2. В `.env` посочете адреса към реалния MongoDB:
   ```env
   MONGODB_URI="mongodb://localhost:27017/famas"
   JWT_SECRET="academic_defense_secret_key_2025"
   ```
3. Попълнете базата с данни:
   ```bash
   npm run seed
   ```
4. Отворете **Mongo Express** на `http://localhost:8081` за да покажете колекциите и документите на живо пред комисията!

## 7. Автоматизирани тестове (QA Suite)

Проектът съдържа автоматизирани тестове с **Vitest**, покриващи ключовите изисквания:

```bash
npm test
```

### Покрити тестови сценарии:
1. `tests/fuelAndTrip.test.ts`:
   - Изчисляване на разход на гориво ($L/100km$).
   - Създаване на курс и валидация на задължителните полета.
   - Автоматично начисляване на изминатите километри към километража на камиона при завършване.
2. `tests/rbacAndIntegrity.test.ts`:
   - Хеширане и проверка на пароли чрез bcrypt.
   - Защита на Express маршрути чрез `authorizeRoles` (връщане на HTTP 403 за неразрешени роли).
   - Забрана за изтриване на МПС с активни курсове.
3. `tests/notifications.test.ts`:
   - Генериране на предупреждения за изтичащи прегледи/застраховки.
   - Дедупликация на нотификациите за предотвратяване на спам.
